# tpl v0.1.2 — error messages name the database for every provider

- **Version:** 0.1.2
- **Date:** 2026-11-06
- **Tag:** `v0.1.2`

`tpl` reads the schema of a MariaDB or MySQL database or a SQLite database file
and renders it through MiniJinja templates loaded from disk at render time.
v0.1.1 made the help state each command's behaviour for every provider, but some
error, cause, hint and warning lines still named a server for a fact that also
holds for a `sqlite` entry, and the help of `tpl version` named a fixed release.
This patch release corrects both. It changes no command, flag, exit code,
document key, configuration key or template name.

## Highlights

- **Error, cause, hint and warning lines speak of the database where every
  provider reads one.** A line whose fact holds for a `mariadb`, a `mysql` and
  a `sqlite` entry alike no longer speaks of a server.
- **The help of `tpl version` names no concrete release.** It no longer goes
  stale with each release.

## Changes by area

The full list is the `0.1.2` entry of
[`CHANGELOG.md`](https://github.com/FlavioCFOliveira/tpl/blob/v0.1.2/CHANGELOG.md).

### Fixed

- **`tpl render` with `--context` and `--direct`.** The `cause` line reads
  `--context reads the context from a document and reads no database; --direct demands a read of the database`,
  where it said that `--context` contacts no server, and the `hint` reads
  `remove --direct to render from the document, or remove --context to read the database`.
- **`tpl cache load --no-cache`.** The `cause` line says that `tpl cache load`
  reads the database in order to store what it read, and the `hint` says how
  to read the database without storing, where both spoke of the server.
- **`-d/--database` where it has no effect.** The warning, and the clause a
  refused `tpl cfg database add` or `update` appends, say that the flag selects
  the entry for commands that use one, where they said commands that connect.
- **`tpl version` help.** The text help and `tpl help --format json` describe
  the output as `tpl <version>`, where they gave `tpl 0.1.0`.

### Internal

- The functional specification moves to its 89th edition. `FR-ERR-051` extends
  the provider rule of `FR-HELP-038` to error, cause, hint and warning lines,
  and `FR-RND-041`, `FR-CFG-020` and `FR-CFG-051` are amended to match. The
  technical specification is aligned with it.
- The validate and build jobs of the CI and release workflows are limited to
  30 minutes each.
- The deadline, password-command and SQLite watchdog tests no longer depend on
  wall-clock time; the one check that needs real time is now a measurement
  test, ignored by `cargo test`.
- The `0.1.0` entry of the changelog now labels as breaking the exit-code
  changes that release made: `3159` exits `78`; `1040`, `1203`, `1226`,
  `1129` and every unclassified login error number exit `69`; `1102` exits
  `78`; `tpl cfg database test` exits `69` on an error that is not a privilege
  error; and a short or malformed packet exits `69` instead of `70`. Those
  changes shipped in v0.1.0; v0.1.2 changes no exit code.

## Upgrade notes

No action is required. A script or agent that matches error, cause, hint or
warning text word for word should be checked against the new lines; the exit
codes, the JSON documents and the configuration are unchanged. The Claude Code
skill is unchanged since v0.1.1.

## Installation

```sh
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/tpl/main/install.sh | sh
```

The same command installs and updates `tpl`, into `/usr/local/bin` by default,
or into the directory `TPL_INSTALL_DIR` names. To install or update the Claude
Code skill:

```sh
curl -fsSL https://raw.githubusercontent.com/FlavioCFOliveira/tpl/main/install-skill.sh | sh
```

The release carries one archive per supported target
(`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`,
`x86_64-apple-darwin`, `aarch64-apple-darwin`), the skill archive
`tpl-skill-v0.1.2.tar.gz`, and one `SHA256SUMS` file covering all five
archives. **The archives are not signed.**

## Test evidence

The mandatory validation pipeline was run locally on the release candidate:
`develop` at `3e00bd6` with the version bumped to `0.1.2` and the example
outputs regenerated with the 0.1.2 binary.

| Command | Result |
|---|---|
| `cargo fmt --all -- --check` | exit 0 |
| `cargo clippy --all-targets --all-features -- -D warnings` | exit 0, no warning in `tpl` |
| `cargo build --release` | exit 0; the binary prints `tpl 0.1.2` |
| `cargo test --all-features --no-fail-fast` | exit 0: 1 686 passed, 0 failed, 13 ignored |
| `cargo audit` | exit 0: 154 dependencies scanned, no advisory reported |

The 1 686 tests are 1 249 unit tests, 435 integration tests in 20 suites, and
2 doc-tests.

- **Database fixtures running.** The MariaDB fixture (series 10.11, 11.4, 11.8
  and 12.3, and a server without TLS) and the MySQL fixture (series 8.4 and 9.7,
  each with and without TLS, and an 8.0 server for the refused-series case) were
  started and stopped through their harnesses, so the tests that need a real
  server ran against them.
- **Assertions skipped on this target.** 2 tests skipped their assertion and are
  counted in the passed total: both observe a syscall trace that exists only on
  the two Linux targets.
- **Measurement tests ignored.** 13 tests are marked `#[ignore]` because they
  depend on wall-clock timing or on memory sampling. `cargo test` does not run
  them.
- **Environment:** `aarch64-apple-darwin`, macOS 27.2, rustc 1.99.1.
- **At the tag:** the release workflow re-runs the same five commands on all
  four supported targets before it publishes anything.
